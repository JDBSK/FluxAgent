# 04｜面试表达稿

## 一、30 秒自我介绍（项目版）

我叫 XX，做过一个叫 FluxAgent 的开源项目：一个基于 LangGraph 的本地 Agent 应用。它会规划任务、调用工具、处理失败、审批高风险操作，并且用 SQLite 保存状态，支持会话恢复。项目核心不是 Demo，而是“能把管线跑完、又能防住失控”的工程化 Agent。

## 二、1 分钟项目亮点

我做了三层防线：

1. 执行前 Policy：按工具类型+参数信号把读/写/执行/高危分开，危险调用执行前硬拒；
2. 审批 + 沙箱：写操作进入人工确认，命令只能在白名单沙箱里跑；
3. 预算与恢复：LLM 次数、工具轮次、重试、重规划都有上限，超限熔断，并输出可读原因。

同时，所有路径都有 JSONL 审计日志和运行指标，这是别人 Demo 里通常没有的“生产感”。

## 三、3 分钟架构讲解

> “FluxAgent 的核心是一张 LangGraph 状态图。”

入口 initialize 先重置预算计数；planner 按任务复杂度决定要不要拆步骤；agent 节点决定下一动作：直接回答还是调用工具。

如果调用工具：

1. Policy 评估：只读放行、写/执行审批、明显参数硬拒；
2. 通过后进 approval（HITL）；
3. tools 执行，结果变成 ToolMessage 回传；
4. progress 节点更新计划、检查失败；
5. 失败后走 recovery，根据失败类型决定 retry / replan / abort；
6. 每一步都有预算检查，上下文也会按回合裁剪并压缩成摘要。

用一句话总结：**不是靠提示词约束模型，而是把安全、成本、恢复写进流程本身。**

## 四、常见追问及应对

如果问：

- “你这个和直接 prompt 一个 ChatGPT 有什么区别？”
  → 答：prompt 只能让模型想，不能让它执行；我的系统里有可审计、可恢复、有预算的执行层。

- “为什么不用 OpenAI Function Calling 或单链？”
  → 答：Function Calling 是模型侧能力，我需要的是整个执行链路：策略、审批、恢复、持久化、指标。LangGraph 给我状态和 checkpointer。

- “如果模型选错了工具怎么办？”
  → 答：现象是 description 能力不足，机制是参数校验+失败 replan 兜底；我会优先修工具描述，同时在测试里用“该调用 A 却调 B”这样用例去回归。

- “线上出了死循环怎么办？”
  → 答：先看预算熔断是否启动；更重要的是怎么发现：dashboard 的 llm_calls / tool_rounds / replan_count 会暴露；修法一类是加条件边（重试不动)、一类是预算封顶，一类是计划替换规则。

- “可以并发/并行工具吗？”
  → 答：当前是单线程顺序多步，但工具内部用 async 调 MCP；并行工具是演进方向。
